# REBON.md

This is the canonical instruction file for Rebon workers in this repository. Compatibility files such as `CLAUDE.md` are legacy pointers only and must not override or duplicate these instructions.

This repository holds the CLI. The desktop app and the mobile client ship
separately (<https://reboncode.ai>); the `rebon serve` page ships as the
`@rebon/rebon-web` npm package. Comments below name those surfaces where they
explain why a seam exists — none of them can be opened from this tree.

## Directory layout and naming

```text
crates/
  rebon-*/                    main Cargo workspace crates
  plugins/<feature>/          Rust feature plugins and their companion binaries
services/
  rc-server/                  standalone Remote Control service workspace
  relay-server/               standalone relay service workspace
runtimes/node/
  plugin-host/                our own JS plugin host, not Node.js itself
  compose-runtime/            the plugin composition runtime
  plugins/                    JS plugin packages and the browser extension
assets/
  schemas/                    generated ACP / Web API / session wire artifacts
  web-ui/                     Web UI build output and generated types
i18n/                         internationalization source strings
npm/                          npm distribution wrappers
scripts/                      build, release, check and Git hook scripts
vendor/                       third-party dependencies and local forks
```

- Place things by responsibility: a separately deployed service goes under
  `services/<name>/`, a Rust plugin under `crates/plugins/<feature>/`, and the
  JS runtimes and plugins under `runtimes/node/` and its `plugins/`. Do not
  start a second directory at the root for the same purpose, and do not
  pre-create empty directories for projects that do not exist.
- Project directories use lowercase `kebab-case`; Rust source module
  directories use `snake_case`. Tool-mandated directories, third-party code,
  external protocols and published package/binary names keep their contract.
- A directory name and a package name are not the same thing. The Cargo
  package under `crates/rebon-custom-select/` is still `rebon-customselect`,
  and the Rust import is still `rebon_customselect`.
- The two services keep their own workspace and lockfile, and a root-workspace
  check does not stand in for theirs. Run them from the repository root with
  `--manifest-path services/rc-server/Cargo.toml` and
  `--manifest-path services/relay-server/Cargo.toml`.
- `assets/schemas/acp-wire.json` is generated by `cargo run -p
  rebon-schema-gen` and is maintained together with
  `assets/web-ui/acp/types.generated.ts`; it is not any one service's private
  implementation detail.
- A path in this repository is not an installed path. Reorganizing directories
  must not move user config, plugin install directories or distribution
  layout. When something does move, update the real paths in Cargo,
  generators, asset embedding, CI, packaging scripts, ignore rules and docs —
  do not run a global replace on a bare package name.

## Common commands

```bash
# Whole-workspace checks (run from the repository root)
cargo check
cargo build --release
cargo test                         # runs all 10k+ tests
cargo clippy --all-targets
cargo fmt --all

# Single crate
cargo test  -p rebon-core
cargo check -p rebon-cli

# Single test (substring match against #[test] name)
cargo test  -p rebon-core attachments::tests::poller_injects_once

# Running the binary
cargo run -p rebon-cli --                          # default: local TUI
cargo run -p rebon-cli -- --acp                    # ACP stdio server
cargo run -p rebon-cli -- --provider <name> \
                          --model    <id> \
                          --resume   <session-id>
```

Toolchain is pinned to `stable` via `rust-toolchain.toml`, with `rustfmt` and
`clippy` components.

### Git hooks

`scripts/hooks/pre-push` runs `cargo fmt --all` before every push and stops
the push when formatting moves anything — otherwise a later workspace-wide
format pass buries the next real change under hundreds of unrelated lines.
Install once per clone:

```bash
git config core.hooksPath scripts/hooks
```

Bypass a single push with `git push --no-verify`.

### Running the binary — logging

- `--acp` mode writes tracing output to **stderr**.
- Default (TUI) mode writes to a **file**: `$REBON_LOG_DIR/rebon.log`, falling
  back to `%TEMP%/rebon/logs/rebon.log`. Never log to stdout/stderr in TUI
  mode — crossterm's alt-screen does not cover stderr and it will corrupt
  the screen.

### Packaging

```bash
# User install/update path
npm install -g @rebon/cli

# Maintainer packaging: platform package by default, wrapper/all when requested
python scripts/build_npm_package.py                # reuses target/release/rebon
python scripts/build_npm_package.py --kind all --binary <path>
python scripts/publish_npm_package.py --kind all --dry-run
```

The root `@rebon/cli` wrapper depends on scoped optional platform packages
such as `@rebon/cli-win32-x64`. Publish platform tarballs first and the
wrapper last; scoped `@rebon/*` publishes default to `--access public`. The
workspace release profile keeps existing optimization settings while setting
`debug = 0` and stripping Rust symbols, and the packaging script refuses
accidental `.pdb`, `.dSYM`, `.map`, Rust/TS source, `target`, `dist`, or
`node_modules` payloads. The `.cmd` wrappers hard-code `--build`; invoke the
Python scripts directly if you want to skip a rebuild.

## Architecture — the big picture

### Binary shape

One binary, three surfaces: **cli**, **serve**, **tui**.

**cli** — `crates/rebon-cli/src/main.rs` is a thin clap dispatcher and nothing
else. It parses the global runtime flags (`--provider`, `--model`,
`--resume`, `--continue`, `--bg`, …), the subcommands, and the flags that
select a surface, then hands off. It also *is* the headless surface:
`--acp` runs `acp::run_acp_server`, the JSON-RPC ACP server an IDE or editor
drives over stdio (or over TCP with `--acp-host`/`--acp-port`), handling
`initialize`, `session/{new,load,list,prompt,cancel}`, permission
reverse-RPC, tool-output streaming and transcript persistence. Subcommands
parsed here run before a kernel exists — `rebon remote …` edits the host list
whether or not the remote plugin is enabled, and `rebon __acp-fs-mcp` is the
file-service bridge Rebon spawns for an agent CLI. Real logic never lives in
this crate; it wires and dispatches.

**serve** — `serve::run` puts the same ACP server behind a local web page.
`acp::build_acp_server` builds the handler both ACP surfaces share; `serve`
connects it to an in-memory pipe and multiplexes browser tabs onto it
(`serve/mux.rs`, which also announces every session's turn state and keeps
the token ledger), serves `rebon-web-ui` (a Vite + React + TS ACP client;
its committed `assets/web-ui/dist` is embedded by `crates/rebon-cli/build.rs`,
and `--web-ui <dir>` serves one from disk), and adds the `/api/*` routes for
what ACP has no method for — history, plugin plane, commands + skills, tasks,
agents, MCP, models, usage, rewind, compaction, workspace files. Every
request but the page needs the per-run token. This repository does not
contain the Web UI source project: to update the page, take the build output
from the separate Web UI project, put it in `assets/web-ui/dist` and commit
it, or point `--web-ui <dir>` at an existing build. `cargo build` does not
need Node.

**tui** — the default. `tui::run` is the local ratatui/crossterm interface:
wiring, terminal lifecycle, prompt input, dialog stack, engine session. See
`crates/rebon-cli/src/tui/mod.rs` for the staged layering (`wiring` →
`terminal` → `runner` → `app`/`event`/`dispatch` → `update`).

All three construct the **same engine / model client / publishers** via
`rebon-cli/src/tui/wiring.rs` — any behavior that should be shared between
them lives there, not in any entrypoint. What that wiring calls is
`rebon-harness`: the plugin list, agent and session assembly, and the plane
boot. The desktop app reaches the same assembly through
`build_headless_session`. The ACP-hosted surfaces (`--acp`, `serve`) route
every turn through `session_agent_router::SessionAgentRouter`, which keeps one
`AgentBackendSwitch` + `SessionAgents` per session id so the `agent` config
option can do per session what `/agent` does in the TUI (local engine, a
kernel loop such as `kernel:dsh`, or a declared agent CLI).

### Core flow: query loop

`rebon-core::query::run_query` is the agentic loop. Each iteration:

1. Ask the model client for the next delta.
2. Run any emitted tool calls through `rebon_tool::ToolContext` with a
   permission broker (ACP → `AcpPermissionBroker`; TUI → a channel-backed
   interactive broker).
3. Run the **attachment poller** (`rebon-core/src/attachments.rs`). This is
   where new runtime-state→model injections belong — it is a per-iteration
   hook already wired into `TurnControlPlugin`. Do **not** add such injections by
   committing to the TUI transcript.
4. Emit the public `QueryEvent` stream, consumed by the
   `crates/plugins/agents` runtime, by `rebon-cli`, and by tests.

`spawn_worker` in `crates/plugins/agents/src/runtime/worker.rs` re-enters
`run_query` through a `WorkerSpec` (tool subset, system prompt, iteration
cap, model). A sub-agent is not a second executor: it is the same query loop
run with different inputs.

### Crate layering

Dependencies point inward: surface → assembly → plugins → seats → kernel. Read
the arrows as "declares in its `Cargo.toml`"; nothing below reaches back up.

```
rebon-cli ─┬─▶ rebon-harness ──▶ crates/plugins/*   (assembly: builtin_plugin_defs(),
           │        │                                kernel boot, agent + session
           │        │                                assembly, feature plugins)
           │        ├─▶ rebon-plugin-host   (Node plugin plane, compositions,
           │        │                        manifests, payload patches)
           │        ├─▶ rebon-provider      (provider catalog, runtime cache,
           │        │                        model-router seat, llm adapters)
           │        ├─▶ rebon-kernel-seats  (the built-in Core seats)
           │        └─▶ rebon-core          (also a direct dep of rebon-cli)
           │
           ├─▶ rebon-session-runtime ─▶ rebon-session-host ─▶ rebon-proto
           │        (worker + IPC server)    (job state, owner/lease,
           │                                  the one client every end uses)
           │
           ├─▶ rebon-acp        ─▶ rebon-proto   (server: an editor drives us)
           ├─▶ rebon-acp-client ─▶ rebon-proto   (client: we drive an agent CLI)
           │
           ├─▶ rebon-tui ─▶ rebon-message-tui ─▶ rebon-render
           │                                     (ratatui-free projection
           │                                      every end shares)
           └─▶ rebon-dialog, rebon-picker, rebon-customselect, rebon-spinner, …

rebon-core ─┬─▶ rebon-agent-core ─▶ rebon-api  (Anthropic / OpenAI / OAI-Responses)
            ├─▶ rebon-tool ─▶ rebon-tools-core
            ├─▶ rebon-session, rebon-session-state, rebon-proto
            ├─▶ rebon-kernel, rebon-permissions, rebon-hooks, rebon-instructions
            └─▶ rebon-bridge

leaves (no `rebon-*` dependency at all): rebon-kernel, rebon-bridge,
rebon-tools-core.  rebon-types ─▶ rebon-tools-core; rebon-session ─▶ both.
```

- **`rebon-core` does not depend on `rebon-acp`, and never did in this
  direction.** The ACP server sits beside the engine, not under it:
  `rebon-cli` and `rebon-harness` each depend on both. `rebon-acp` reaches
  `rebon-session`, `rebon-agent-core` and `rebon-kernel` on its own.
- **`rebon-harness` is above `rebon-core`, not beside it.** It depends on the
  engine, on both ACP legs, and on every feature plugin — which is why the
  plugin list can only live there.

- `rebon-tools-core` and `rebon-types` are intentionally dependency-light so
  every higher crate can depend on them without cycles.
- **`rebon-session` is not an ACP concern.** It owns the on-disk JSONL
  transcript schema, project directory keying, session locks, rewind, and
  file-history snapshots — used identically by ACP, the TUI, the desktop app,
  and background jobs. Depend on it directly: the session host lives in
  `rebon-session-host`, not under the old `rebon-background` crate name, and
  the `memory` plugin depends on it directly too. `rebon-acp`
  deliberately does **not** re-export these names; routing through it will
  not compile. It also owns `memory_paths`: where a project's durable-memory
  directories are is the same config-home-plus-project-key fact, and the file
  tools have to recognise those paths without depending on the memory
  feature.
- `rebon-proto` is the direction-agnostic ACP wire layer (framing,
  transport, JSON-RPC + ACP types). `rebon-acp` is the **server** side — the
  one an editor drives over stdio. `rebon-acp-client` is the **client** side —
  Rebon spawning a third-party agent CLI and driving it. The two share
  `rebon-proto` and deliberately do not depend on each other.
- **The ACP client leg cannot promise everything the local leg does.** Rebon
  advertises `fs/read_text_file` + `fs/write_text_file` so an agent's file
  access comes back through the host and can be snapshotted, but nothing
  forces an agent to use them — `AcpAgentBackend` reports
  `writes_through_host_fs` from the wired-in `HostFs`, and `DirectHostFs`
  (the default) answers `false`. ACP also reports no token usage, so
  **session reuse rate**, not cache-hit rate, is this leg's efficiency signal.
- **An ACP turn is still a Rebon turn on disk.** `TurnJournal` /
  `TranscriptJournal` write the prompt, the agent's text, its tool calls, and
  the paired tool results into the session transcript in the same shape the
  engine writes, so `--resume`, `/rewind`'s turn list, and a later switch back
  to the local engine all see the real conversation. Two rules there are
  load-bearing: every `tool_use` gets a `tool_result` (an unfinished one is
  closed out as an error, because a dangling `tool_use` is a message no model
  accepts), and thinking is streamed but **not** recorded, since an unsigned
  extended-thinking block renders fine and fails to send. The projection is
  hand-written JSON matching `rebon-api`'s `ContentBlock`; the drift test that
  keeps them honest is
  `rebon-cli/src/tui/acp_agents.rs::an_acp_turn_replays_as_messages_the_local_engine_can_send`,
  which runs a recorded turn back through `transcript_to_api_messages`.
- **A remote host is an agent CLI with `ssh` in front of it.** The
  `remote` plugin (`crates/plugins/remote`) owns ssh argv, the
  `remotes.json` store, remote platform detection, and the install
  scripts; it deliberately does not depend on `rebon-acp-client`. Its
  `agents` module turns a host into a `DeclaredAgent` under the id
  `remote:<name>`, so `/agent`, the agent list, the session sidecar,
  and the transcript journal work on a remote without learning what ssh
  is. Remote names reject `:` and agent ids carry the prefix, so the two
  namespaces cannot collide.
  Two fields separate a remote from a local agent, and both follow from
  the filesystem being elsewhere: `workspace_cwd` carries the *remote*
  project path into `session/new` (the session's own cwd names a
  directory on this machine), and `inject_fs_tools` is off, because the
  injected `rebon __acp-fs-mcp` would be spawned on the far side of the
  connection where it cannot reach this host's fs service. A remote is
  also given no write roots, so a host-side write cannot land on a
  same-named local path, and it is kept out of the sub-agent pool,
  whose routed writes assume local roots. Adding a third client surface
  (the desktop app) means reusing `rebon-plugin-remote`, not re-deriving
  the ssh command.
  The declarations reach a session through the kernel, not through an
  import: `rebon_agent_core::declared_source` is the seat the plugin
  registers on and `session/build.rs` reads, so `plugins.remote.enabled
  = false` takes every `remote:` agent out of `/agent`, the agent list
  and `/context` at once. `rebon remote …` stays: it is clap
  subcommands parsed before a kernel exists, and being able to edit the
  host list while the feature is off is the right way round.
- **`--remote` is a demand, not a preference.** The configured default
  agent falls back to the local engine with a warning when it cannot be
  reached; `--remote` fails the session instead. Falling back would run
  the user's prompts against the one filesystem they ruled out by
  naming another machine. It fails two different ways on purpose: with
  the plugin disabled nothing can name the host and the message says so,
  while a named host that will not answer is reported as the host it is.
- **Two surfaces declare an agent CLI; only one thing runs it.** `acpAgents` in
  `config.json` (can carry `env`/`cwd`) and `runtime: acp` frontmatter (cannot)
  both normalise into `acp_agents::DeclaredAgent` before anything spawns, so
  "how to start an agent CLI" is described once. A name on both surfaces
  resolves to `config.json` — the definition winning would launch the CLI
  without the key the user configured. Add a third surface the same way: map it
  to `DeclaredAgent`, do not teach the spawn path about it.
- **Session-level agent choice is `/agent`.** It swaps the backend behind
  `AgentBackendSwitch`, which is why every holder of the session's
  `Arc<dyn PromptExecutor>` sees the change without being rebuilt. The choice
  and the agent's own session id live in the session sidecar
  (`save_session_agent` / `save_agent_session_id`), so a resume reopens on the
  same agent with its context — and an explicit switch back to `local` is
  stored as a choice rather than decaying into "follow the config default".
- **A background job named after an external agent runs *on* it.** The worker
  builds its session through the same `build_tui_session`, so it inherits
  `session_agents`; `resolve_background_agent_runtime` returns
  `external_agent` instead of a system prompt and tool filter, and the worker
  switches the session before the turn. That is also what makes such a job
  visible in Agent View as itself — it already has a row and a session id, and
  the journal puts the agent's turns in that session's transcript, so opening
  the row shows the real conversation. A named agent that cannot be reached
  **fails the job**: falling through would run a general-purpose local worker
  under that agent's name.
- **`rebon-agent-core` is the turn seam, and it is direction-neutral.** It owns
  `PromptExecutor`/`PromptRequest`/`PromptOutcome` (run one turn), the
  `SessionUpdatePublisher` + permission-request sinks a running turn publishes
  through, and `AgentBackend` — which agent runs the turn at all, plus the
  `AgentCapabilities` it admits to. These lived in `rebon-acp` until the ACP
  client needed them; import them from `rebon-agent-core`, not through
  `rebon-acp`, which no longer re-exports them.
- **`AgentCapabilities` is a promise, not a hint.** A backend that answers
  `writes_through_host_fs: false` is saying Rebon never saw its writes, so
  `/rewind` has nothing to restore. Gate the feature on the capability rather
  than letting the UI offer a no-op.
- **`runtime:` in agent frontmatter picks the leg.** Omitted (or `local`) means
  Rebon's engine; `runtime: acp` + `command:` + `args:` means a third-party CLI.
  External agents appear in the agent list and `/context`, but
  `AgentRegistry::spawnable()` keeps them out of the Agent tool's
  `subagent_type` list and dispatch refuses them — the coordinator's worker path
  only runs Rebon's own loop, so offering one would silently spawn a
  general-purpose local worker under that agent's name.
- `rebon-bridge` (the Remote Control protocol and client, RFC-0008) **is a
  root workspace member**, so `cargo check --workspace` and `cargo test
  --workspace` cover it. What keeps it separable is its `dependency_contract`
  test — it must never depend on a `rebon-*` crate — not an exclusion from
  `members`. Its `http` and `ws` features are off by default; `services/rc-server`'s
  dev-dependency is what compiles them in CI.
- `rebon-core` is the integration layer — the model/tool loop lives here.
- `rebon-cli` is only wiring + dispatch. Real logic lives in other crates.

## Conventions that are load-bearing

- **Tests are not optional per change.** Every Rust change ships with a
  coverage matrix, not just a happy-path test. A change with only one or two
  tests is not done.
- **Keep mobile golden baselines in sync.** Any mobile UI change that affects
  golden rendering must update the corresponding images, then verify the
  targeted golden tests without `--update-goldens` and run the full mobile
  test suite.
- **Never enable `serde_json`'s `arbitrary_precision`.** Cargo unifies features
  across a build graph, so one crate turning it on turns it on for every crate
  compiled beside it — and with it on, `serde_json` yields numbers as maps
  through `deserialize_any`, which is the path `#[serde(tag = "...")]` and
  `#[serde(flatten)]` take. Around 45 internally-tagged enums here carry numeric
  fields, the model wire types among them. `rebon-plugin-protocol` needed exact
  number tokens and reached for the feature; it took `cargo test --workspace`
  down, and CI missed it because CI runs per-crate `-p` tests, each with its own
  feature graph. Use `raw_value` and keep the text (see
  `rebon-plugin-protocol/src/payload.rs`);
  `rebon-plugin-protocol/tests/no_arbitrary_precision.rs` fails if the feature
  comes back.
- **Runtime-state → model injections go through the attachment poller**, not
  through TUI transcript commits. See `rebon-core/src/attachments.rs`.
- **Leaf crates stay leaf.** `rebon-bridge` has a compile-time compatibility
  test forbidding any `rebon-*` dep. Preserve that invariant if you edit it.
- **The vendor behind an endpoint is a table, not a host check.**
  `rebon-api/src/vendor.rs` is the one place that knows what changes per
  company on an OpenAI-compatible wire: the thinking switch spelling,
  which effort values are accepted, whether the output cap is
  `max_tokens` or `max_completion_tokens`, which fields the vendor rejects,
  whether historical `reasoning_content` must be replayed, whether the
  prompt cache is prefix-keyed (which puts the prune middleware in
  cache-stable mode), and where the model list lives. It is resolved from
  the entry's `vendor` pin or `baseUrl` host into
  `ResolvedProvider::vendor` and handed to the client as
  `OpenAiCompatibleClientConfig::vendor`; the request builder rewrites
  the body to that dialect last, so a `thinking` object a config wrote
  for DeepSeek still comes out as `enable_thinking` for Qwen. Every row
  cites the vendor's documentation page. Do not add a
  `contains(".deepseek.com")` anywhere; add a row.
- **Provider runtimes are cached, not rebuilt per call.** A sub-agent that
  names a provider resolves through
  `rebon-provider/src/provider_runtime_cache.rs`, keyed by case-folded
  provider id and gated on `config.json`'s (mtime, len) so an edited provider
  entry takes effect immediately; entries idle past the TTL are dropped on a
  later lookup. Only runtimes marked `provider_runtime_cacheable` are shared:
  external plugin clients (no `fork_for_sub_agent`, connection-scoped
  lifecycle notifications) and OAuth providers without a 401-refresh
  middleware are rebuilt on every call, exactly as before the cache existed.
  Live session state (the fast/service-tier toggle) is re-applied on every
  cache hit, never cached. If you add a provider-resolution path, route it
  through the cache and let the cacheability flag decide sharing.
- **`/compact` compacts now, and the result is a file.** At an idle prompt the
  command runs `ResumeReplayHandle::compact_now` on a worker thread (progress
  in `rebon-cli/src/tui/compact_widget.rs`, driven by
  `runner/compact_runtime.rs`) and installs the compacted history through
  `install_persistent_summary`, which writes
  `<project_dir>/<session_id>.compact.json`. The sidecar is not an
  optimisation: a background job rebuilds its `TuiEngineSession` — and with it
  the whole `ReplayWindowStore` — for every turn, so an in-memory baseline
  would be dropped before the turn it was meant to shrink ever ran. A baseline
  whose anchor row or prefix hash no longer matches the transcript is deleted
  and the turn replays full history; never fail a turn over a stale one. Only
  the mid-turn path still arms `force_compact_once`, because the running turn
  owns the live `ContextManager`.
- **Don't use `println!` / `eprintln!` in TUI code paths** — it will land
  inside the alt-screen surface. Use `tracing::{info,warn,error}`; the TUI
  wiring routes logs to a file.
- **Tool names and permission behaviors** live in `rebon-tools-core` as
  shared primitives (`ToolId`, `PermissionBehavior`, `PermissionDecision`,
  `PermissionRequest`). New tools register against these types, not against
  ad-hoc strings.

## Coding rules

Four principles; every trade-off below traces back to one of them:

1. Split by reason to change: code that changes for different reasons does not
   share a function or a file.
2. Dependencies point inward only: surface (cli / app / serve) → plugin →
   kernel. Break any dependency that runs the other way.
3. Delete before you abstract: code that can be deleted does not get an
   abstraction layer written for it.
4. One mechanism per concern: when the same thing has a second implementation,
   delete the second one instead of writing an adapter.

These rules are held by review, not by a counter. There was a ratchet that
scored some of them — one tool-name list, no long functions, no silently
swallowed lock poisoning — against a budget file, and it is gone. A count
tells you a number moved, never whether the change behind it was right, and
the number is what a raise then negotiates with. Read the change instead.

`crates/REBON.md` holds the specific rules for the `crates/` tree.

### Error handling

- Take a lock with `x.lock().expect("<lock name> poisoned")`. `if let Ok(g) =
  x.lock()`, `.ok()`, `.unwrap_or(0)` and `Err(_) => return` all skip the
  critical section in silence when the lock is poisoned; the test is whether
  information was lost. `unwrap_or_else(PoisonError::into_inner)` is a
  deliberate recovery — do not turn it into `expect`. Every access to one lock
  handles it the same way.
- An operation that cannot fail gets `expect("<why it cannot fail>")`, not
  `let _ =`.
- On a startup path, fail outright when `current_dir()` / `current_exe()`
  cannot produce a real path; do not substitute `"."`. When spawning our own
  process, do not use the bare name `rebon` — PATH will find a different build.
- Validate external input only (network protocols, user files, subprocess
  output); do not re-validate data you just constructed or just wrote.
- Retry at one level, with backoff. Do not stack a retry on top of a lower
  one.
- Do not put `#[serde(default)]` on an `Option<T>` field; it does nothing.
- Before adding a cross-crate dependency to merge a few similar fragments,
  price the dependency edge. If it costs more than the merge is worth, do not
  merge.

### One fact, written once

- Write files atomically with `rebon_session::{write_file_atomically,
  write_private_file_atomically}`; take the config directory from
  `rebon_session::config_home`; read boolean environment variables through
  `rebon_types::env`; take millisecond timestamps from
  `rebon_types::wall_clock_ms`. Call them by their full path, without aliases.
- An encoder and its decoder are maintained together in one crate: the
  implementation lives in the writer's crate and the reader imports it. The
  same goes for constant-time comparison and XML escaping — one copy only.
- Merging duplicate functions requires all four: byte-identical bodies, a
  dependency edge that already exists, the same types involved, and a merged
  location that makes conceptual sense. Pure functions can merge; inventing a
  shared state struct in order to merge means do not merge.
- Re-exporting through a façade crate is not decoupling. Coupling is how many
  places in production code reach through it, not how many lines
  `Cargo.toml` has.
- A decision rule is written once, in a named function, next to the field it
  decides.

### Splitting functions and refactoring

- Keep a function under 300 lines of production code; split it into named
  stage functions with behavior unchanged and not one original comment lost.
- A sender, guard or handle that was moved into the function must not become a
  clone or a borrow when it is extracted. A `.clone()` added to satisfy the
  compiler keeps the original alive to the end of the function, which changes
  when it drops and can leave the receiving end waiting for a close that never
  comes. After splitting, grep for the name and compare HEAD against the
  working tree line by line.
- Ownership transfer that used to rely on "the function returns immediately"
  becomes an explicit `mem::take` or a hand-back through the return value,
  with a comment.
- After splitting, check for same-name shadowing such as `let x = <expression
  containing x>`; keep local variables from sharing a name with a free
  function in the same module; give each extracted struct field exactly the
  type the original local had.
- In a labelled long loop, label both `continue` and `break`.
- When there are too many parameters, define a struct for that group of state
  rather than threading one more level.
- Handle every unreachable expression, unused parameter and constant bool
  parameter the compiler reports after a split. Do not add `allow`.
- Update comments when code moves or is deleted; check for dangling references
  with `cargo doc -p <crate> --no-deps`. A comment that contradicts the code is
  a defect.
- A prompt template's placeholders need a test that exhausts the substitutions;
  a magic upper bound gets a constant name and a reason.

### Finding and deleting dead code

- Dead code has to satisfy all of: no reference outside the crate, no
  reference inside the crate, and not a module declaration file — and the last
  step is reading the code. Grepping by module path misses `pub use`
  re-exports and multi-line `use {...}`, so treat it as a lead only.
- A serde compatibility variant (an enum variant kept to read old files) is not
  dead code by reference count.
- Run `cargo check --all-targets` before deleting any symbol; looking at
  warnings from the bin target alone will delete code the tests use. To tell
  whether something is test-only: `cargo check` reports it and `cargo check
  --tests` does not. `touch` the file first, or cargo's cache will hand you a
  convincing zero-warning run.
- A claim of "no references anywhere" ships with the grep command and its
  output.
- Remove `#[allow(dead_code)]` and let the compiler report. Delete along the
  call chain until nothing new is dead, and delete an enum variant together
  with its match arms.
- Dead code sometimes means a feature was never wired up, or that it is the
  second implementation of the same logic. Record it and confirm before
  deleting.

### Moving and deleting code

- Use a unique anchor for string replacement and assert that it matched
  exactly once; check the order of magnitude of the diff line count before
  committing.
- Anchor an insertion at the top of an item (before its own `///` comments) or
  at the end of the file; delete a function starting from the first line of its
  comment. Afterwards check three things: the total comment line count, whether
  a stray `//` is left at the end of the function, and whether each `///` above
  a function still belongs to that function.
- Line endings are not uniform in this repository (both CRLF and LF): detect a
  file's line ending before a script edits it, read and write with
  `newline=''`, and match paragraph ends with `\r?\n`.
- Edit code with the Edit / Write tools. A Bash heredoc turns escape sequences
  such as `\n` into real characters. Write a commit message to a file and use
  `git commit -F`.
- Run rustfmt only on the leaf files you changed; running it on `main.rs` or
  `mod.rs` reformats the submodules with them. Finish with a per-file
  `rustfmt --check` and read only the `Diff in` lines.
- Changing a function signature means changing every call site in the same
  pass; do paired changes in one write, or run `cargo check` after every step.
- Widening visibility while moving code is fine as long as you narrow it back
  in the same batch of work. The one case that may stay widened is a test
  constructing an internal type across modules, and it is stated as such.
- Give estimates as orders of magnitude, and report the measured value
  alongside the gap from the estimate and why.

### Tests and verification

- A new crate is added to CI's test list. Before saying "CI will catch it",
  look at what CI actually runs.
- Fixing a defect starts with a test that fails before the fix.
- Tests do not depend on mtime ordering, line endings, the current directory,
  or a real repository's git history.
- When a timing-sensitive test fails, run it three times on its own before
  attributing the failure; the standard is the same machine and the same
  `--exact --nocapture` command, run once on a clean HEAD and once with the
  patch.
- A `#[tokio::test]` that touches subprocesses or the plugin plane uses
  `flavor = "multi_thread"`, and a test that started the plugin plane ends with
  `plane.shutdown().await`. A test that reads or writes environment variables
  or the config directory holds a `TestConfigHome` guard.
- Put `#[cfg]` on an assertion that only holds on one platform, and branch on
  `is_available()` before asserting that a tool exists.
- A silently skipped test did not run (plugin-plane tests need
  `REBON_TEST_NODE`). Run several packages' tests separately, with
  `--no-fail-fast` to see the whole picture.
- An example program that is not in the build graph rots without telling you.

### Dependencies and runtime structure

- Untangle a backwards dependency with a new leaf crate or by sinking the type
  into a lower crate — not with an adapter layer. A zero-dependency crate's
  dependency constraint is a contract; when it needs an outside capability,
  inject a callback.
- Group a large struct's surplus fields by feature into an extension table
  (`extensions`), and pin the field-count ceiling with a test.
- Before adding polling, prove there is an asynchronous event to wait for.
- Persist a failure result and say explicitly who may clear it; give startup
  paths a timeout; have a plugin refuse at load time rather than waiting for
  bind.
- Offer APIs with and without a timeout in pairs; the timeout branch sends
  cancel, releases the waiting call, and returns `HostUnanswered`.
- Put failure in the return type (`Result`) instead of making the caller test a
  string prefix; give a one-shot asynchronous result a monotonically
  increasing id and drop results whose id does not match.
- Shut the plugin plane down before the process exits; do not paper over a
  hang with `shutdown_timeout`.
- Steps that must happen together live in one function, pinned by a test that
  checks the end state; merge two duplicated code paths before changing
  either.
- An object reused across turns is lent and returned explicitly, not reclaimed
  by scanning a snapshot; projected data has an authoritative source behind it
  or an explicit expiry; a singleton gets an explicit type or function name
  rather than being implied by `Option::get_or_insert_with`.
- Permission-related extension points are fail-closed.
- A kernel context's `fork` shares the service registry with its parent; use
  `fork_scoped` when a separate namespace is needed, and keep registration and
  removal symmetric.

### Commit messages

- English only. Subject line `type(scope): imperative sentence`, at most 72
  characters, no trailing period; `type` is one of feat / fix / docs /
  refactor / test / chore / ci / build / perf / merge / release, and `scope` is
  the short crate name (cli, tui, core, session-host, plugins/<name>).
- Ticket and slice numbers stay out of the subject line (no `T27 ——`, no
  `E3-R5 ——`); write them as a `Ref: T27` trailer at the end of the body.
- The body says what changed and why: a defect fix states the root cause, a
  judgement call states the judgement. No narrative, no test counts, no line
  counts, no worker names. Wrap the body at 72 characters.
- A merge commit reads `merge: fold <work package>`, with the parenthetical
  explanation in the body.
