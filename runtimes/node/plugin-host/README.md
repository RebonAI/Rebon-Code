# Rebon Node plugin host

This package is the zero-dependency ESM stdio host for the plugin protocol. Standard output is exclusively NDJSON protocol frames; diagnostics and host console methods write bounded, single-line JSON to standard error.

The supported runtime is Node `>=24.19.0 <25`, enforced by `rebon-node-runtime`; a Rust test reads this file, `package.json`, and the release workflow back so the four copies of that range cannot drift. The implementation may be logically exercised on older Node versions, but that does not validate the supported runtime.

Plugins are trusted local code, equivalent to installing a native editor extension or npm package. This host is not a sandbox, and trusted code can still access `process.stdout` directly. The supported package surface is the SDK root export and the `rebon-plugin-host` executable; repository-relative deep imports are for trusted in-repo code and are not an isolation boundary. Method payload schemas for `plugin/load`, `plugin/unload`, `service/call`, `event/deliver`, `event/subscribe`, `event/unsubscribe`, and `event/emit` live in `src/methods.mjs`, mirroring `crates/rebon-plugin-protocol/src/methods.rs`; the shared corpus at `crates/rebon-plugin-protocol/tests/fixtures/v1/methods.json` requires both languages to reach the same verdict and the same bracketed refusal code on every case, including one that pins name length to UTF-8 bytes rather than UTF-16 units. `src/loader.mjs` loads a plugin's entry module and collects what it registered; the registrar refuses a service or topic the manifest did not declare, and registration closes when `activate` returns. `plugin/load`, `plugin/unload`, `service/call`, and `event/deliver` are handled, and the host itself calls `event/subscribe` upward when a scope opens for a plugin that registered topic handlers — a subscription is a topic handler bound to one scope incarnation, so it cannot be made before there is a scope to pin it to. Frames are handled concurrently rather than one at a time: a request handler may call rebon and the answer arrives on the same stream, so awaiting each dispatch before reading the next would deadlock. The consequence is that terminals come back in completion order, not arrival order; they are matched by call id. A handler is called as `handler(request, ctx)`; that `ctx` is bound to the scope incarnation the call arrived on and carries `invoke(tool, input)`, which sends `tool/invoke` upward. It is the only thing a plugin holds that reaches back into rebon, and it refuses a tool the manifest's `tools` list did not declare before anything is sent, so the error names the plugin's own line. The identity on the call is injected by the host rather than reported by the plugin. The same `ctx` carries `emit(piece)`, which sends a `chunk` frame on the handler's own call: a call may carry any number of chunks and still exactly one terminal, and the context closes when the handler returns, so a captured context cannot emit into a call the caller has finished reading. An llm adapter is a service under a different routing key: declared as `llmProviders` in the manifest, registered with `plugin.llm(provider, adapter)`, and answered with chunks and then a return value. The `ctx` also carries `signal`, raised when rebon sends `call/cancel` — cancel asks rather than commands, so a handler may ignore it and finish, and a handler that throws because it was cancelled ends the call as `cancelled` rather than as an error. A plugin's own tools are registered with `plugin.tool(definition, handler)` and called back through `tool/call`. Unlike a service, a tool has to be *offered* to a model, so the registration carries a description and input schema rather than a name alone; a description is bounded and may not be empty, because it is spent out of every turn's context budget for as long as the tool is offered. The manifest keeps the two tool directions in separate lists — `tools` for what the plugin provides, `invokableTools` for what it may call — and neither stands in for the other. A handler's own exception fails that call (`[HANDLER_FAILED]`) rather than the host: only a transport failure is fatal. A plugin's entry module is called as `activate(api, config)`: the package says what the plugin can do, the load request's `config` says what this installation wants it to do, and the host reads none of it. What a plugin package *is* is itself replaceable: `rebon-plugin-host --loader <module>` points the host at a module exporting `createLoader({next})`, which decides how a package is loaded and is told when a plugin has finished draining so it can take down whatever it built — a Cordis composition realm, say. The host itself knows one shape (`activate`) and hands anything else to the loader; a host that cannot build the loader it was pointed at refuses to start rather than quietly loading a different set of plugins. `plugin.scope(handler)` asks for a handle on each session the plugin is opened for, carrying `publish`/`seat`/`invoke` bound to that scope incarnation and nothing else — it is what a plugin that acts on its own schedule (an agent loop producing turn events) uses, since it has no inbound call to hang a message on; the handle refuses (`[SCOPE_CLOSED]`) once its incarnation ends, and the same declarations gate it as gate a call context. `ctx.publish(topic, event)` sends `event/emit` upward — the other half of the event plane from `event/deliver`. It is declared as `publishedTopics`, kept apart from the `eventTopics` a plugin listens to, because hearing a topic and being able to announce one are different powers; a plugin that declared only the listening side is refused with `[UNAUTHORIZED_TOPIC]` before anything is sent. `ctx.seat(seat, method, params)` reaches rebon's kernel seats, declared as `seats` in the manifest and gated the same way invokable tools are. It is a request, so it has an answer — and therefore cannot serve a synchronous teardown path; what a disposer depends on has to be a declaration the protocol unwinds on unload, not a call made on the way out. Cordis/dsh integration and sandboxing are out of scope for this host — plugins are trusted local code.

Rust keeps payloads as their exact JSON text (`serde_json`'s `RawValue`, never `arbitrary_precision`, which would change number handling for every crate compiled alongside the protocol crate), so both sides preserve a token neither language's float can hold. Inbound JSON is scanned before JavaScript number conversion. Identity integers are validated from their exact decimal token. Opaque payload integer tokens within the JavaScript safe-integer range become numbers; other payload number tokens become frozen `RawJsonNumber` values carrying the original token. Such values must be interpreted by a method-specific schema before sending them again; the writer rejects implicit re-encoding rather than rounding them. The `engines` field is package metadata; runtime management lives in `crates/rebon-node-runtime` (`rebon node status/install/uninstall`), which gates resolution on the same range, installs a verified runtime under the config home, and hands the resolved executable to background workers. This host claims no supervision, launching, or crash recovery of itself.

The shared Rust/Node differential corpus has 66 named exact-byte cases and an expected SHA-256 for every case. Node 22 can exercise protocol logic during development, but only the Node 24.19 gate in `.github/workflows/release.yml` proves the supported runtime. Cross-language process coverage uses the workflow's absolute controlled executable in `REBON_TEST_NODE` with `REBON_REQUIRE_TEST_NODE=1`, which turns a missing executable into a test failure instead of a local skip.

The call ledger commits at most one terminal before attempting the write. A callback-time write failure leaves that terminal committed as a tombstone and the process fails; this is an at-most-one commitment guarantee, not terminal-delivery liveness. It does not claim crash fail-all, restart, leases, supervision, distribution, or plugin isolation.
